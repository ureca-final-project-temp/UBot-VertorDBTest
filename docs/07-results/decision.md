# 비교 결과 해석 기준

기준은 [최신 620개 측정의 6축 산포도](fairness-v2-results-20260913.md)다. 실제 프로젝트는 청크 1,000~10,000개를 예상한다. 현재 결과는 합성 10k·Top-10·동시성 10의 탐색 자료이며 최종 DB 선택이나 서비스 적합성을 확정하지 않는다.

## 무엇을 비교하는가

1. 비슷한 **실제 Recall**의 설정끼리 지연·QPS·자원을 비교한다. 서로 다른 검색 파라미터를 평균 내어 가상의 한 구성으로 만들지 않는다.
2. 같은 생성·검색 설정의 5회 재구축을 함께 본다. Recall은 평균/범위, p95·QPS는 회차별 지표의 중앙값, 자원은 평균 CPU 및 회차별 peak RAM의 중앙값을 사용한다. 범위는 신뢰구간이나 서비스 최저 보장이 아니다.
3. 무필터 Recall–무필터 p95와 필터 Recall–필터 p95를 분리한다. 혼합 QPS는 evaluation 200개 전체 부하이고, 혼합 Recall은 빈 정답 6개를 제외한 194개에 대한 점수다.
4. Recall 0.80·0.90·0.95는 참고선이다. 필요하면 ±0.01 범위 및 가장 가까운 실제값을 명시하되 목표값으로 치환하거나 범위 밖 점을 없애지 않는다. 최근접값은 동등 품질 보장의 대체물이 아니다.
5. p95/QPS/RAM만 있는 그림은 해당 설정의 Recall 그림과 함께 읽는다. 낮은 Recall의 빠른 점과 높은 Recall의 느린 점을 속도만으로 줄 세우지 않는다.

## 실행 예산과 선정 조건을 분리한다

| 구분 | 현재 의미 | 처리 |
|---|---|---|
| 4 vCPU / 8GiB / swap 없음 | 대상 배포의 공통 실행 예산 | 측정 환경 조건으로 기록 |
| OpenSearch 4GiB heap | 의도한 JVM 시작·최대 힙 | 관측 RAM의 배경으로 설명 |
| RAM 관측값 | Docker 표본의 DB 배포 메모리 | 상대 비교 지표; 최소 필요 메모리 아님 |
| 2GiB RAM·30ms p95 | 합의되지 않은 코드 기본 임계값 | 이번 제품 판정에 사용하지 않음 |
| 서비스 요구 SLO | 아직 확정하지 않음 | 확정한 기준처럼 PASS/FAIL하지 않음 |

RAM을 줄여 다시 측정하지 않고 기존 관측치를 사용할 수 있다. 단, 메모리 설정이 다른 새 측정과 동일 조건이라고 합치지 않는다. OpenSearch가 4GiB 힙을 쓰도록 설정했는데 2GiB 상한으로 탈락시키면 실행 조건과 선정 조건이 충돌한다.

## 오류·경고·미검증을 별도로 기록한다

| 상태 | 현재 기록 | 해석 |
|---|---|---|
| 검색 실패·응답 계약 위반 | 각 0건 | 실행 실패와 낮은 Recall은 다른 문제 |
| 자원 증거 불완전 | 0행 | 표본 수·구간 보존; 호스트 전체 비용 아님 |
| 워밍업 조건 미충족 | 170/620행 | 경고 표시, 원시값과 5회 집계에 포함 |
| Milvus DISKANN 반복 Recall 변동 | 5행 | 원인·상태 동일성 확인 전 재현성 결론 보류; 점 유지 |
| 독립 holdout·실데이터·1k | 미실시 | DB 실패가 아니라 아직 하지 않은 검증 |

경고가 있는 회차를 삭제해서 좋은 결과로 교체하지 않는다. 경고가 없다는 이유로 모든 DB의 안정성을 동등한 절차로 증명했다고도 쓰지 않는다.

## 기존 decision.eligible의 취급

[DecisionGate.java](../../src/main/java/com/myapp/benchmark/DecisionGate.java)는 임계값이 없으면 Recall 0.95·p95 30ms·RAM 2GiB를 적용하며, holdout·워밍업·자원·오류 조건도 하나의 verdict로 합친다. 이 로직은 현재 코드에 남아 있다. 따라서 과거 필드뿐 아니라 **이번 최신 summary의 decision.eligible도 제품 탈락 판정으로 사용하지 않는다.**

이번은 전체 그리드를 evaluation으로 살펴본 exploratory다. split이 존재해도 이 결과로 후보를 고르는 행위는 독립 holdout 검증이 아니다. 문서에서는 후보 검토와 최종 검증 단계를 구분하며, 코드가 이미 수정되거나 holdout을 통과했다고 주장하지 않는다.

## 최종 선택으로 넘어가는 조건

현재 산포도 → 실제 1천~1만 청크·서비스 질의/필터/Top-K 고정 → pgvector exact 대조군과 후보 ANN 비교 → 후보를 고정한 별도 질의 검증 → 운영·정합성·복구 비용 검토 순서로 진행한다. 100k/1M은 성장 검증이 필요할 때의 선택 실험이다.

최종 제품·shortlist·서비스 SLO는 이 문서에서 자동 결정하지 않았다. [최신 보고서](fairness-v2-results-20260913.md), [지표 정의](../03-benchmark-design/metrics.md), [한계](../03-benchmark-design/limitations.md)를 함께 읽는다.
